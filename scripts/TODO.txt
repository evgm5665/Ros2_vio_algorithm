This is the largest conceptual gap in the instructions.

There are two different things called “FRD”:

- Body FRD: axes attached to the vehicle.
- Local FRD world frame: a fixed local world frame whose initial horizontal heading defines its X/Y axes.

Do not apply R_frd_flu blindly to every quantity. The transformation depends on what frame the input quantity is expressed in.

You need to confirm these facts from the actual OpenVINS message:

- What does header.frame_id contain?
- What does child_frame_id contain?
- Is position expressed in the OpenVINS global frame?
- Is twist.linear expressed in the child/body frame or global frame?
- Is OpenVINS’s body convention FLU?
- What orientation does the quaternion represent—body in world or world in body?

For standard nav_msgs/Odometry semantics:

- Pose is expressed in header.frame_id.
- Twist is expressed in child_frame_id.
- The quaternion normally represents the child frame’s orientation in the header/world frame.

But verify OpenVINS follows those semantics before implementing the multiplication order.

A practical definition for local FRD:

When the first valid OpenVINS sample arrives:

1. Save its position as the local origin.
2. Extract or otherwise establish the initial heading.
3. Build a fixed rotation from OpenVINS world coordinates into your local FRD world coordinates.
4. Save that rotation and translation.
5. Set alignment_valid = True.
6. Increment reset_counter when this origin is later re-established.

Then position conversion has the conceptual form:

p_output = R_output_openvins × (p_openvins - p_origin)

Do not set alignment_valid=True until you have clearly defined and tested this transformation.

For now, implement only local_frd. If frame_mode == "ned", log an error or warning and refuse publication. True NED requires an external or global alignment that arbitrary-yaw OpenVINS does not provide.


STAGE 8: HANDLE ORIENTATION CAREFULLY

Orientation needs transformations on both sides:

output-world ← OpenVINS-world

and:

ROS body FLU → PX4 body FRD

You cannot safely choose the quaternion multiplication order until you write down what every quaternion means. Use notation such as:

q_A_B = orientation of frame B expressed in frame A

Then derive the chain using matching frame labels. This prevents the most common error: using the right fixed rotations in the wrong multiplication order.

After calculating the output quaternion:

1. Normalize it.
2. Compare it with the previous output quaternion using the dot product.
3. If the dot product is negative, negate all four components.
4. Store it in PX4 order [w,x,y,z].

Negating a quaternion does not change its rotation; it only maintains a continuous numerical representation.
